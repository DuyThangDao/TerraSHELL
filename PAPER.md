Abstract The emergence of DevOps is accompanied by an increased use of Infrastructure as Code (IaC) to specify and manage deployment configurations, infrastructure, and associated resources. Terraform is one such IaC solution. However, improper configurations can lead to serious security threats. This paper introduces an approach, implemented as TerrARA, that provides a systematic and structured way for automatically eliciting security threats based on Terraform configuration files. Specifically, TerrARA: (1) automates the con-struction of an abstract model—an enriched Data Flow Diagram (DFD)—from Terraform configuration files for Amazon Web Ser-vices (AWS), and it can be extended to other resources and cloud providers via profiles; (2) encodes cloud computing threat patterns, which are utilized by the SPARTA threat modeling engine to auto-matically identify security threats; and (3) demonstrates its capa-bility in accurately extracting DFDs from Terraform projects and eliciting relevant cloud computing security threats, achieving high accuracy and reasonable performance compared to existing tools and approaches like StartLeft and GPT-4o. By integrating it into CI/CD pipelines, the automated reconstruction and analysis enable continuous security assessments that systematically incorporate cloud infrastructure artifacts into the threat modeling process.

1 Introduction With the emergence of DevOps, the software development process has accelerated through the application of principles, practices, pro-cesses, and automation tools that bridge the gap between software programming and deployment. A DevOps environment commonly relies on Infrastructure as Code (IaC): configuration files are used to automatically deploy and manage key system resources, such as cloud storage and services, databases, network policies, access management, and more [17]. IaC, cloud technology, and infras-tructure automation in general address challenges related to time, complexity, reliability, and scalability. Therefore, IaC is widely used in software projects and businesses [8].
Various articles have raised security concerns for IaC [13, 18]. Thus, a number of techniques have emerged to assist in detecting security vulnerabilities in IaC configuration files through various methods such as static analysis (e.g., checkov [4], tfsec [26]) or security smell detection [21, 23, 24]. These tools andmethodsmostly focus on detecting implementation security bugs, such as hard-coded secrets, use of weak cryptographic algorithms, and suspicious comments. However, there is still very little systematic research on inspecting architectural security flaws in IaC, such as broken access control or insecure storage, to support security-by-design.
Threat modeling, also known as architectural risk analysis (ARA) [37], is an activity that inspects software architecture to identify potential security weaknesses in the underlying software or system and to propose suitable solutions for these issues. Ideally, software developers and security experts conduct threat modeling in the design phase of the software development process to detect poten-tial architectural flaws (e.g., broken access control). However, this analysis can also be performed on existing projects.
Manual threat modeling is a time-intensive activity and typically requires software design documents, which are often outdated or unavailable [5]. This challenge highlights the need for automated threat modeling to expedite the process and overcome the lack of design documents. In the context of IaC, configuration files can thus be a promising foundation for automated threat modeling, as they reliably reflect the product’s current state and capture the deployment architecture. Furthermore, similar to IaC deployment

Despite the need for automated threat modeling based on IaC configuration files, there is a noticeable lack of tools and research in this area. StartLeft [11] is one of the few tools available that perform automated threat modeling on IaC configuration files, including Terraform, one of the most widely used IaC platforms. However, the tool has some limitations, such as not fully detecting data flows between different components and trust boundaries, and failing to recognize a component as a process or data store in the extracted representation of the IaC, which could potentially lead to missed relevant security threats (more details in the Section 5). This high-lights the ongoing need to improve automated threat modeling based on Terraform configuration files. The main challenge lies in bridging the gap between the fine-grained level of detail of the configuration files and the coarse-grained abstraction at which architectural threats for cloud environments (e.g., the catalog of Brazhuk [2]) are typically described.
This paper introduces an automated security threat modeling ap-proach for Terraform configuration files, implemented as TerrARA, with the following contributions:
(1) an automated approach to extract an abstract representa-tion of Terraform configuration files for Amazon Web Ser-vices (AWS), in the form of an enriched Data Flow Diagram (DFD). Currently, 29 AWS service types are supported, and the approach can be extended for other resources and cloud providers via Profiles (Section 4).
(2) an encoding of 72 cloud computing threat patterns, which are used by the SPARTA threat modeling engine [29] to automatically identify these threats in the extracted model (Section 4).
(3) an evaluation of the performance of TerrARA, the accuracy of the DFD extraction compared to existing tools and ap-proaches, the relevance of the elicited threats, and the exten-sibility for identifying other cloud provider resources (Sec-tion 5). The evaluation also demonstrates the weaknesses of other tools and approaches and highlights TerrARA’s ad-vancements over these limitations.
2 Related work Automating threat modeling activities is crucial to reduce the time and effort needed for the process. Many researchers have studied this area, with most focusing on extracting DFDs and attack sur-faces directly from the source code. Berger et al. [1] proposed a technique to extract the security architecture of Java-based business apps from source code and perform threat modeling to detect secu-rity flaws. Tran et al. [34] presented a framework that systematically enumerates the attack surface of Android applications based on source code, and created new threat-type catalogs to aid in Android apps threat modeling. Schneider et al. [25] developed a technique to extract detailed annotation DFD from the Java source code of microservices. However, none explored Terraform configuration files for threat modeling. IriusRisk introduced the StartLeft [11]
tool supporting automated threat modeling from Terraform con-figuration files. This tool provides the detection rules in separate files, which users can extend for detecting additional resources. However, StartLeft has several limitations, including its focus on processing independent Terraform configuration files rather than entire projects. Additionally, it does not comprehensively detect all components and information necessary for accurately extracting the representation of the IaC system. Furthermore, there is a lack of studies evaluating the effectiveness of IaC threat modeling tools like StartLeft. Sørum [31] introduced a semi-automated threat modeling of cloud-deployed applications via IaC configuration files, i.e., AWS CloudFormation, not Terraform. This method involves extracting the DFD from configuration files, but it requires assistance with manually tagging resources to accurately identify DFD entities. The utilized threat catalog is generic and limited. Additionally, it has not been thoroughly evaluated. While there are limited tools that support threat modeling for IaC, many tools focus only on visualiz-ing the structure of IaC, such as InfraMap [6] and Rover [19]. For instance, InfraMap generates provider-specific graphs that high-light the most important and relevant resources to showcase the structure of the IaC, but it does not provide enough information (e.g., process, data store, trust boundary) for threat modeling.
Regarding the IaC security static analysis and security modeling, Rahman et al. [23] performed qualitative analysis on IaC scripts to detect seven security code smells, such as admin by default and empty password. Saavedra et al. [24] conducted a large-scale empirical study on technology-agnostic security smell detection and identified nine different security smells in Puppet, Ansible, or Chef scripts. Opdebeeck et al. [21] proposed a technique that utilizes Program Dependence Graphs to identify seven security issues in Ansible code. This approach provides crucial information such as data flow and control flow details. The study found that over half of security issues relate to data flow indirection, with one in three involving dynamic file inclusion. This highlights the necessity for advanced static analysis tools to detect IaC vulnerabilities.
Research on static analysis for IaC is limited, particularly in ex-tracting data flow or control flow information for security threat modeling. While static analysis detects vulnerabilities like exposed secrets and insecure configurations, it falls short in identifying archi-tectural security risks and design-level threats. These approaches are equally important, complement each other, and collectively support a comprehensive security assessment.

3.2 Security Threat Modeling Threat modeling is an activity that analyzes the representation of the system being built to identify potential security threats and propose corresponding solutions [14, 28]. However, it does not in-volve risk evaluation, which is a distinct step within the broader risk assessment process. Four common steps in the threat model-ing are [14, 28]: (1) Create a representation of the application; (2) Identify the potential security threats (threat elicitation); (3) Deter-mine countermeasures to address the threats; and (4) Evaluate the
results. The Data Flow Diagram (DFD) is one of the most popu-lar and recommended system representations for threat modeling, apart from formal system models, logical architecture diagrams, and sequence diagrams [16, 32]. Figure 1 shows both an AWS cloud architecture [32] and the corresponding DFD representation. Pro-cesses (circles) are the entities that perform computational or logical functions by processing the input to produce dedicated output (e.g., AWS API Gateway). Data stores (parallel lines) are where the data is kept at rest (e.g., AWS S3 Bucket). External entities (rectangles) are the objects outside the system that can communicate with the components inside the system (e.g., User). Trust boundaries (red dashed rectangles or lines) separate the system into parts with different levels of security or trust. Data flows (arrows) represent how data moves between the components. Threat catalogs (e.g., STRIDE [28]) can be applied to the DFD to elicit potential security threats the system can face. An example of a security threat is when an unauthorized threat actor can make API requests through the AWS API Gateway process to extract sensitive data stored within AWS resources, such as AWS DynamoDB.
4 TerrARA: Design and Implementation The primary objective of TerrARA (TERRaform configurations-driven Architectural Risk Analysis) is to support the threat mod-eling process (Section 3.2) by extracting the DFD representation from Terraform’s configuration files (step 1 of threat modeling) and listing all potential security threats (step 2 of threat modeling). Gaining a deeper understanding of the system being built and the security threats that can harm it not only helps software develop-ers and security experts create a more efficient product but also increases the security awareness of the whole project.
In a manual modeling process, analysts would model the appli-cation (the Terraform configuration files in our case) according to their goals and targets. This poses the following challenges: (1) de-termining which part of the source code will be modeled as a DFD component; (2) classifying the type (e.g., data store) for modeled DFD components by investigating their functionality; (3) identi-fying the data flows between components; and (4) composing a collection of cloud-related threats and choosing the threat frame-work to elicit relevant threats.
The following sections address the mentioned challenges. Our proposed approach, implemented as the TerrARA tool, consists of three main phases (Figure 2):
(1) Preprocessing (Phase 1 - Section 4.1): This phase analyzes the configuration files in the Terraform project and converts them into a resource dependency graph, which captures the creation relationships between resources. These relation-ships are helpful in identifying data flows in the next phase.
(2) Graph Analysis (Phase 2 - Section 4.2): This phase applies pattern matching, graph query and analysis on the resource dependency graph, to create the service dependency graph and then map service nodes to suitable DFD elements based on the documented functionality of these cloud services to create the DFD. The extracted DFD are enhanced with the annotations to produce enriched DFD as the output. The rules for extraction are defined in a customizable Profile.

The implementations of the TerrARA phases are explained below.
4.1 Phase 1: Preprocessing In Phase 1, all the necessary information is extracted from the Ter-raform configuration files and organized in a structured way for further analysis. To achieve this goal, the Preprocessing module first uses terraform graph [10] to get the descriptions of the relationships between objects (e.g., resources) in Terraform config-uration files. Terraform provides the graph utility to construct an internal dependency graph from the configuration files [10] and the Terraform State file to provide the order or dependency of resource creation. For example, if resource A depends on B, this means that resource B should be created before resource A (Fig-ure 3). This utility produces a .dot file of the directed dependency graph (Figure 4).
The output graph from terraform graphmight contain orphan resource nodes. Orphan resources refer to any resources that are present in the state file of Terraform but no longer exist in the configurations [10]. Thus, these orphan nodes do not reflect the current context of the Terraform configuration. To cope with this problem, this module uses the terraform-graph-beautifier [3] in the second step of this phase to remove orphan nodes and export the
result in JSON format. A graph database (memgraph [15]) is used to load the dependency graph for efficient graph analysis.
The directed dependency graph contains many types of nodes that are associated with Terraform’s block types (Section 3), such as variable block, module block, and data block. However, this work focuses only on the resource nodes to extract the DFD. The other intermediate nodes (e.g., variable nodes) are removed, and the relationships between the remaining resource nodes are rewired (based on the relationships in the directed dependency graph) to create a resource dependency graph (Figure 4). Each resource node contains a resource name (an arbitrary string) and a resource type: a Terraform constant string (e.g., aws_instance) which is defined by the cloud provider (e.g., AWS). The resource dependency graph is the output of phase one.
4.2 Phase 2: Graph Analysis In this phase, graph queries, pattern matching, and graph anal-ysis are used to extract entities from the resource dependency graph, constructing an annotated DFD. First, we build a service dependency graph, grouping resource nodes into services for a higher-level abstraction. This graph is then analyzed, guided by a customizable Profile. The Profile contains a set of yaml files that define the pattern matching and annotation rules, ownership rela-tionships, and complex static analysis rules. These rules are then used by semgrep (Section 4.2.4). The matching rules are based on the specific characteristics of each cloud provider, such as Ama-zon Web Services (AWS), Microsoft Azure (Azure), and Google Cloud Platform (GCP). Each cloud provider platform has its own implementation and resources in the Terraform configuration. De-velopers can add more rules or create new Profiles to enable the Graph Analysis tool to identify custom DFD entities that fit the context of their software projects. Currently, we only focus on rules for AWS due to its popularity.
Figure 4 illustrates the conversion of Terraform configuration files to a DFD in Phases 1 and 2. We continue by explaining the different substeps of phase 2 in more detail. The DFD elements enumeration substeps (e.g., process detection, data store detection) are inspired by the work of Berger et al. [1].

A process (or a component) is an object that consumes input data to compute a corresponding output. The level of abstraction or decomposition of the process will depend on the framework, the application context, and the goals of developers or security experts. In the context of AWS, the processes are computational or logical services, such as AWS EC2 (compute platform) and AWS Lambda (serverless, event-driven compute service). To detect processes, the Process Detection submodule traverses the nodes in the service dependency graph and performs the pattern matching of tf_name in the Profile and the resource type of the node. The matched nodes are also assigned the corresponding annotation (i.e., cloud application, virtual machine, container) as declared in the Profile (Listing 2). For example, Listing 2 presents a rule to identify the AWS Amplify service as a process and is annotated as a cloud application by matching the resource node aws_amplify_\w*. The compress flag is true, meaning that the resource nodes have to be consolidated to represent a single AWS Amplify service.
4.2.2 Data Store Detection. Themechanism of detecting data stores is similar to the process detection. The Data Store Detection sub-module leverages the pattern matching rules in the Profile (Listing 2) to identify popular AWS storage or database nodes in the service dependency graph to be added as a data store in DFD and assigns the corresponding annotation.
4.2.3 Entry/Exit Points Detection. The main objective of this sub-module is to support the detection of external entities not present in the configuration files but that can be detected indirectly through entry and exit points. These points, where data enters or exits a system, are the only means for external entities to interact with the application. In this work, the exposed AWS resources in Terraform are considered entry and exit points with interfaces or APIs to communicate with the outside world. Determining the exposable services in Terraform and AWS is quite challenging, as it depends on factors like access credentials, public IPs, and network settings. An overapproximation is made by considering all potentially expos-able AWS services [22] as entry and exit points, each corresponding to an external entity and annotations (i.e., remote user, external service). A Profile can declare a service as exposable by setting the can_public flag.
4.2.4 Trust Boundaries Detection. Determining trust boundaries can vary depending on the context of the analyzed system. In the case of Terraform and AWS, we consider trust boundaries to be the network settings, such as the Virtual Private Cloud (VPC) and subnet, which are also presented as service nodes in the service dependency graph and are detected by the pattern-matching rules in the Profile. Then, other DFD elements are arranged within trust boundaries by custom rules.
Services within the same VPC can communicate directly using the defined CIDR block, which is divided into subnet CIDR blocks. There are two types of subnets: public and private. A public subnet connects to an Internet Gateway, allowing communication with external resources, typically to manage traffic through a bastion host EC2. Services in a private subnet can communicate only with other services in the same VPC. Because public subnets expose resources to the outside, the trust boundaries for public subnets are removed. The detection rules are written in semgrep [27], a contextual static analysis pattern matching frame-work, making this detection extensible for other cloud platforms. A subnet is identified as public if the aws_subnet resource has map_public_ip_on_launch = true or through graph pattern and attribute analysis (Figure 6). Once identified, public subnet nodes are removed, and their inbound and outbound nodes are linked to maintain data flows. All rules are configurable in the Profiles to adapt the characteristics of the cloud providers or the conventions of the working projects.
Positioning processes and data stores within trust boundaries in a DFD requires understanding the dependencies between re-sources. A trust boundary acts as a resource node and can depend on other resource nodes, either directly or indirectly. For AWS, the subnet boundary typically falls within a VPC boundary. The ar-rangement process involves two steps. First, dependencies between trust boundaries are analyzed to determine the hierarchy.Second, the dependency relationships between processes or data stores and their associated trust boundaries are identified to place elements within the innermost trust boundary. This step is crucial, as a pro-cess or data store may be linked to multiple trust boundaries in the dependency graph.
4.2.5 Data Flows Detection. The dependency graph represents the relationships between nodes based on the dependencies of Ter-raformresource creations. We assume that if two resources depend on each other, there is a data flow between them. Thus, data flows between components (e.g., processes, data stores) are determined by these dependencies, which can be direct or indirect via non-resource nodes like input variables and output values. An overapproximation approach is used, considering data flow between two components as always bidirectional. Additionally, entry and exit points have data flows connected to external entities.
4.3 Phase 3: Threat Elicitation For the automated threat elicitation, TerrARA leverages the existing SPARTA threat modeling engine [29]. The input for SPARTA is a DFD, which can be enriched with element annotations and security countermeasures [30]. In our case, these annotations indicate which elements represent the cloud application, remote users, etc., allow-ing us to find more precise threats by using this additional data extracted from the Terraform sources. For the threat elicitation itself, TerrARA contains a new IaC-specific threat type catalog that can be used by SPARTA. This cata-log is constructed by implementing the 66 patterns fromBrazhuk’s [2] catalog of Academic Cloud Computing Threat Patterns (ACCTP). Each threat pattern description is processed and implemented as a SPARTA threat type, making use of the relevant annotations (e.g., cloud application, virtual machine, container, etc.) from the Profile (Listing 2). As the ACCTP lacks threats related to data stores, the catalog is further extended with six additional threats. In total, Ter-rARA thus includes a catalog of 72 IaC-specific threat types, which is more fine-grained and IaC-specific than SPARTA’s default, six generic threat types (STRIDE).
The concrete implementation of the threat types in the SPARTA catalog uses VIATRA model query [36] patterns. Figure 7 provides a simple graphical illustration of a threat pattern that involves the communication between an external entity and process, where these elements have, respectively, the RemoteUser andCloudApplica-tion annotations. The pattern is derived from the threat description of ACCTP, such as victims, aggressors, and corresponding elicited security threats and solutions. These patterns can be much more complex with alternative annotations, elements, or even completely different patterns for alternative conditions. SPARTA uses these patterns to subsequently search for all instances of these patterns in the provided DFD model to obtain the list of concrete threats (e.g., broken access control).
5 Evaluation We evaluate TerrARA with four experiments, covering (1) the per-formance in terms of running time, (2) the accuracy of the ex-tracted DFD, (3) the relevance of the elicited threats as indica-tors for potential security vulnerabilities, and (4) the extensibil-ity towards other cloud providers. Due to the different evalua-tion targets, we use distinct datasets for each experiment while maintaining the representative properties of the datasets. The Ter-rARA tool, the benchmark, and the full evaluation are published at https://github.com/DistriNet/TerrARA.
5.1 Performance The performance experiment dataset consists of 470 open-source Terraform projects for AWS on GitHub, randomly crawled via ShiShoDojo [7] to ensure practicality.Wemeasure the time required to execute all three phases of TerrARA (i.e., including terraform graph and SPARTA). The median execution time is 42 seconds, ranging from 10 to 54 seconds. The majority of the time is spent on constructing the dependency graph and preprocessing (77%), 8% of the time is spent on the Graph Analysis phase, and the remaining 15% is spent eliciting the threats via SPARTA. The DFD typically comprises an average of 10 DFD entities and results in an average of 47 threats for these projects. We conclude that the performance is adequate for inclusion in a CI/CD pipeline to execute automated threat modeling.

We illustrate the accuracy of each method in more detail us-ing the cloudgoat (glue_privesc) case (Table 3). TerrARA can detect most DFD entities (Figure 8), arrange them in correct trust bound-aries, and include the names of services and annotations for further inspection. TerrARA also detects data flows between services by relying on the dependency graph. The enumeration of trust bound-aries and the arrangement of services within these boundaries are advantages of TerrARA. TerrARA also detects intermediate ser-vices such as IAM and Security group and its data flows, which are very important for security analysis. Other diagrams do not contain these services (except StartLeft, which contains some of them) because they are not significant in terms of functionality.
TerrARA also has some limitations. Because of the incomplete node consolidation, some nodes are dangling and are not merged into the others, which leads to false positive services such as S3 (bucket_notification) and its associated data flows. The overapproxi-mation of exposed resources also causes connections from external entities to various services (such as Lambda (s3_to_gluecatalog) and S3 (cg-data-s3-bucket)) that should be omitted. TerrARA misses the implicit communication, such as the data flows between Glue (cg-glue-connection) and SSM Parameter (cg-secret-string). This in-formation is contained in the properties or policy description of resource nodes, but is not present in the resource dependency graph. Further static analysis and inspection are needed to analyze such communications.
StartLeft cannot fully detect the data flows between the compo-nents and trust boundaries (Figure 9b). StartLeft can only analyze each .tf file independently, so that data flows between components cannot be efficiently detected. This tool does not detect external entities, and does not classify the elements as process or data store. StartLeft detects the entities at the resource level and does not perform the node consolidation to create the service graph like Ter-rARA. This approach may lack abstraction, as individual resources are not consolidated into compact services or components.
The documented architecture diagram (Figure 9a) and InfraMap’s graph (Figure 9c) only show representative components and the relationships between them (high precision), yet omit relevant infor-mation for threat modeling, such as trust boundaries, less important components or entities, and data flows (low recall). Omitting these less critical components leads to false positive data flows, which skip the intermediate nodes (e.g., Security group (cg-ec2-security-group) and shorten the connections (e.g., data flows between User and EC2 (cg-linux-ec2)) in the documented architecture diagram. Thus, the output of InfraMap visualization tool is not sufficiently comprehensive to serve as a representation of the Terraform con-figuration for threat modeling.
The outputs of GPT-4o (Figure 9d) capture many DFD entities, resulting in a higher number of TPs compared to StartLeft and In-fraMap. However, the DFD extraction with GPT-4o faces challenges, such as it produces many FPs, including made-up data flows and trust boundaries (and unmerged cloud resources in other samples). This LLM-powered approach also produces many FNs, including undetected services (e.g., security group, IAM) and misclassification of DFD entities. Regarding the whole dataset, the F1-score of this approach is higher than others but still lower than TerrARA, which also has a better stability property. The evaluation also highlights that while tools like StartLeft perform poorly in DFD extraction, simpler approaches, such as using GPT-4o, achieve better accuracy, making this approach promising for future exploration.

6 Discussion This section elaborates on the limitations of relying on IaC inputs to construct DFDs for threat analysis. The disadvantages include DFD extraction limitations (i.e., implicit communication, creating new complex rules, node consolidation) and threat elicitation limitations (i.e., threat prioritization).
6.1 Implicit Communication While the infrastructure configuration files provide a rich source of operational information on application deployment and the types of cloud services involved, they do not capture all forms of communi-cation between these elements. There are two types of implicit links that may not be correctly captured by TerrARA: implicit depen-dencies through identifiers and implicit communication through third-party services.
Even if all relevant resources are managed by Terraform, it is still possible–in the way they are encoded in the Terraform configuration–to have implicit links between them. A common example is hard-coded identifiers. For example, in Listing 1 the aws_iam_instance_profile has a role attribute that refers to the aws_iam_role name, thereby explicitly encoding the depen-dency. If instead, the profile would specify the name of the role as a string, there would no longer be a dependency between these elements. To avoid these implicit links requires some care in how to specify the configuration in Terraform.
The second form of implicit communication is the reliance on third-party dependencies or indirect interactions not managed by Terraform Terraform. For example, if services rely on DNS lookups to retrieve system addresses but the DNS records are not defined in Terraform, these implicit dependencies remain invisible in the Terraform dependency graph. Only explicitly managed resources
with properly encoded references (without hard-coded identifiers) can be considered in DFD reconstruction.
6.2 Creating Rules for Complex Additional Resources and Cloud Providers
Creating new rules manually for additional cloud resources can be time-consuming, though the complexity varies (some require in-depth graph analysis, while others are relatively straightforward). It demands a thorough comprehension of the resource’s implementa-tion and graph pattern. Therefore, to complete this task accurately, it is necessary to refer to official documents and seek help from cloud engineering experts. Promising approaches to reduce manual effort include LLM-assisted rule generation, community-driven rule contributions, and automated extraction of security patterns. For validating community-contributed profiles, official documentation is the most authoritative source, but a structured validation pro-cess is crucial. This challenge is common in community-driven approaches (e.g., Semgrep’s vulnerability detection rules). Potential solutions include development team reviews, cross-validation by contributors, test-driven validation with required test cases, and automated checks using provider APIs to verify attribute accuracy.
6.3 Nodes Consolidation Not combining nodes in the DFD makes it overly complex and difficult for threat modeling. Yet the node consolidation may pro-duce dangling nodes which leads to false positives. Because of the complexity and variation of the graph patterns of each resource, designing a method for consolidating every resource is quite chal-lenging. Selecting the representative node for consolidated resource nodes and their supporting nodes is also a problem that needs a more fine-grained rule pattern. Further extensive research is re-quired to write rules for node consolidation, as it necessitates a profound comprehension of graph patterns for each resource type.
6.4 Threat Prioritization The elicited security threats for a Terraform configuration can lead to (too) many threats, so that developers need guidance on which threat to tackle first. There are also false positive threats derived from the overapproximations when extracting DFDs. Therefore, more effort is necessary to develop a methodology for ranking and highlighting the most significant threats.
7 Conclusion This paper introduced a threat modeling approach, implemented as the TerrARA tool, for Terraform IaC configuration files (supports 29 AWS service types), which automatically extracts an annotated DFD model and elicits cloud-related security threats (72 threat types). The evaluation demonstrates the effectiveness of the approach. The current version of TerrARA has limitations, particularly in handling implicit communication between components and in cases of over-approximation leading to false positives. There are several opportu-nities to integrate with other code-based approaches that analyze the application source code in order to obtain a more comprehen-sive model of both the application itself and how its components are deployed, enabling an end-to-end security analysis.
